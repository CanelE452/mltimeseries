## TiRex-2 를 이 Windows PC 에서 돌 수 있는지 실측

사용자 질문: "tirex2 윈도우에서 못 돌려? 우분투여야돼?"

앞선 턴에서 내가 "Windows 에서 그대로는 못 돌린다"고 한 것은 공식 README 만 읽은 추정이었다.
실제로 설치해서 돌려 보니 CPU 는 된다. 아래는 전부 실행 결과다.

### 이 PC 조건

Windows 11 (10.0.26200), RTX 4070 12GB (compute capability 8.9), conda base python 3.13.
`cl.exe` 없음, `nvcc` 없음, Docker 없음, WSL 없음 — 넷 다 `where`/`ls` 로 확인.

### 만든 환경

conda env `mlts` (python 3.11.16). base 는 `libiomp5md.dll` 이 중복 초기화되는 OpenMP 충돌이
있어 재사용하지 않았다.

```
conda create -y -n mlts python=3.11
pip install torch --index-url https://download.pytorch.org/whl/cu128   # 2.11.0+cu128, 2.75GB
pip install tirex-2                                                    # 0.2.1
```

`tirex_2-0.2.1-py3-none-any.whl` 은 순수 python 휠이고 OS classifier 도 없다. 패키지 자체엔
플랫폼 제약이 없다. 막히는 것은 의존성 쪽이다.

### 막힌 지점 3개와 각각의 정체

1. **import 자체가 실패** — `xlstm/blocks/slstm/src/cuda_init.py:34` 가 모듈 최상위에서
   `torch.utils.cpp_extension.include_paths(device_type="cuda")` 를 호출한다.
   `CUDA_HOME` 이 없으면 `OSError`. `device` 인자를 보기도 전이라 cpu/cuda 둘 다 죽는다.
   해당 블록은 `if torch.cuda.is_available():` 안에 있고 하는 일은 `CUDA_LIB` 경로 문자열
   계산뿐이다. 그래서 `CUDA_HOME` 을 아무 실재 디렉터리로 지정하면 통과한다 (실측).

2. **CPU 인데 `cl` 을 찾음** — `tirex2/model/component/residual_block.py:9` 의 `@torch.compile`
   과 `attention_block.py:45` 의 `torch.compile(flex_attention)` 때문에 TorchInductor 가
   C++ 컴파일러를 부른다. `InductorError: Compiler: cl is not found`.
   `TORCH_COMPILE_DISABLE=1` 로 eager 실행하면 통과한다 (실측).
   (앞서 "tirex2 에 torch.compile 없음"이라고 적었던 것은 20여 파일 중 2개만 grep 한 오류다.)

3. **CUDA 는 fused sLSTM 커널을 런타임 컴파일** — `flashrnn` 이 `torch.utils.cpp_extension.load`
   를 부른다. `ninja` 는 env 의 `Scripts/` 에 설치돼 있으나 PATH 에 없어 먼저 실패했고,
   PATH 에 넣으면 다음 단계인 `where cl` 에서 실패한다. MSVC 가 필요하다.

### 되는 조합

```bash
export CUDA_HOME="C:/Users/User/anaconda3/envs/mlts"   # 아무 실재 디렉터리면 됨
export TORCH_COMPILE_DISABLE=1
python -c "from tirex2 import load_model; m = load_model('NX-AI/TiRex-2', device='cpu')"
```

정확성 확인 — context 를 `sin(t/8)`, t=0..127 로 주고 32스텝 예측.

| 스텝 | 정답 `sin(t/8)` | 모델 median |
| --- | --- | --- |
| t=128 | -0.2879 | -0.283 |
| t=129 | -0.3944 | -0.394 |

### CPU 속도 (context 512 -> horizon 96, batch 1, 3회 평균)

| 변량 수 | 시간 |
| --- | --- |
| 1 | 87 ms |
| 7 (ETTm2 규모) | 271 ms |
| 21 (Weather 규모) | 847 ms |

batch 를 키웠을 때의 amortize 효과는 재지 않았다. 위 수치는 `forecast([ts])` 단건 기준이다.

### GPU 우회 시도 — Triton 백엔드는 이 GPU 에서 실패

`flashrnn` 에는 `vanilla` / `vanilla_fwbw` / `cuda` / `cuda_fused` / `triton_fused` 백엔드가
있고, `tirex2/model/component/flashrnn_slstm.py:341` 의 `_flashrnn_backend()` 가 device 로
`cpu|mps -> vanilla`, `cuda -> cuda` 를 하드코딩한다. Triton 3.8.0 이 Windows torch 휠에
포함돼 있어 이 함수를 monkeypatch 해 `triton_fused` 로 돌려봤다.

커널 컴파일까지는 갔으나 실행에서 죽었다.

```
OutOfResources: shared memory, Required: 270336, Hardware limit: 101376
```

RTX 4070 (Ada) 의 SM 당 공유 메모리 한계를 넘는다. block size / num_stages 를 줄이면
될 수도 있으나 커널 튜닝이 필요한 영역이라 여기서 멈췄다.

### 결론

- 우분투가 필수는 아니다. Windows 에서 CPU 추론은 환경변수 2개로 실제로 된다.
- GPU 를 쓰려면 MSVC Build Tools + CUDA Toolkit 12.8 설치가 필요하다.
  FlashRNN CUDA 커널이 Windows 에서 실제로 빌드되는지는 아직 미확인이다.
- WSL2 + 우분투가 가장 확실한 GPU 경로다. 이 PC 엔 WSL 이 설치돼 있지 않다.

### 도중에 고친 것

첫 실행에서 Chronos-2 가 두 번 다 실패했다. 내가 쓴 스크립트가 `predict()` 에
`quantile_levels` 를 넘겼는데 그 인자는 `predict_df()` 쪽이다. 실제 시그니처는
`(batch, n_variates, history)` 를 받아 `(n_variates, n_quantiles, horizon)` 리스트를 돌려주고,
quantile 레벨은 `pipeline.quantiles` 에 있다. 두 모델 모두 레벨 목록에서 0.5 를 찾아
median 을 뽑도록 고쳤다 (인덱스 하드코딩 제거).

### 합성 양성대조군을 세 번 다시 설계했다

첫 설계(백색잡음 patch 의 합)는 두 arm 모두 MSE 0.98 로 아무것도 학습하지 못했다.
목표 분산이 0.128 이라 0 을 예측하는 게 거의 최적이었다. 단위분산으로 재척도해도 같았다 —
백색잡음의 정확한 선형 범함수라 학습 신호가 없었다.

같은 구조로 실데이터를 돌려 원인을 갈랐다. ETTm2 3000 update 후 test MSE 0.2235 로
seasonal-naive 0.2660 을 이겼다. 구조 문제가 아니라 과제 문제였다.

두 번째 설계(짝수 patch 전체가 공유 레벨 α, 홀수가 β)는 두 arm 모두 MSE 0.0095 로 풀었다.
32개 그룹에 역할을 공간적으로 분배하면 horizon 없이도 두 정보를 다 보존할 수 있어서다.
**이건 검사의 결함이 아니라 메커니즘에 대한 사실이다** — 공간 분배가 horizon 조건화의
실질적 대안이고, H_STATIC arm 이 그걸 재는 자리다.

세 번째(그룹마다 독립 목표값 32개)는 decoder 가 예산 안에 아무것도 못 배웠다.

네 번째가 통과했다 — 그룹마다 독립 레벨 a_g, b_g, 짧은 미래는 32개 a 의 평균,
긴 미래는 32개 b 의 평균. a 가 서로 독립이라 공간 분배로 우회할 수 없다.
C 가중치 0.999(H=96) 대 0.147(H=336), 분리 0.813, RI +50.7%.

TiRex-2 는 `PARTIAL_HORIZON_UNSUPPORTED`. 두 가지 이유가 겹쳤다.

1. GPU 불가 (flashrnn 이 fused sLSTM CUDA 커널을 런타임 컴파일, MSVC·CUDA Toolkit 없음).

2. **최대 예측 길이가 320 스텝**이라 H=336 을 지원하지 않는다. 실제로 확인한 값이다

   돌려준다. autoregressive 로 이어붙이는 것은 저자가 정의하지 않은 사용법이라 하지 않고
   `BLOCKED_CONTRACT` 로 남겼다.

pretrained 모델이 fine-tuned pilot 을 대체로 앞섰다. 학습 조건이 다르고
(zero-shot 대 target-fitted) pretraining 중복도 확인하지 않았으므로 비교로 쓰지 않는다.

| --- | --- |
| 파일 그대로 | `16a82bd2833779...` |
| 줄바꿈을 LF 로 바꾼 뒤 | `5640e72140efab...` |
| 기록된 값 | `5640e72140efab...` |

원인은 Windows 텍스트 모드다. 해시는 `json.dumps` 가 만든 LF 문자열로 계산했는데
`open(path, "w")` 가 파일에 CRLF 를 썼다. 내용은 같고 줄바꿈만 달랐지만, 지시문 §3 이
요구하는 "companion 파일로 검증 가능한 해시"가 성립하지 않는 상태였다.

`run.py` 를 바이트 모드(`"wb"`)로 고치고, 기존 산출물의 줄바꿈을 LF 로 정규화했다.
재계산 결과 기록값과 일치한다.

`execution_spec.json` 의 `code_hash = 324c04b66d7d68da...` 는 freeze 시점(실행 직전)에
5개 모듈로 계산한 값이다. 커밋된 `run.py` 는 그 뒤 위 CRLF 수정이 한 건 들어가 해시가
다르다. 그 수정은 spec 파일을 바이트로 쓰는 것뿐이고 학습·평가·판정 경로를 건드리지
않는다. 지시문 §19 대로 영향받은 stage(spec 파일 기록)만 다시 수행했고, 나머지 산출물은
재계산하지 않았다. `figures.py` 와 `references.py` 는 core 이후에 만들어진 파일이라
freeze 시점 해시 대상이 아니다.

   보였다. 같은 합성 과제의 joint 목적에서 C 가 I 보다 7.6배 나빴다 (joint MSE I 0.01945
   대 C 0.14819). 나는 H=96 셀과 가중치 분리 0.813 만 강조하고 H=336 셀을 reading_note 로
   치워 뒀는데, 그게 과했다.
2. "seed 잡음 5.05% 라 1% 는 해상도 밖" → 5.05% 는 arm I 의 절대 변동이다. C-I 짝 차이의
   seed 변동은 측정하지 않았고, 둘이 초기 상태·스케줄을 공유하므로 훨씬 안정적일 수 있다.
3. "DENSE−U 3.72% 가 최대 여유폭" → 학습된 DENSE 는 oracle 이 아니다. 6개 cell 중 2개에서
   압축된 C 가 이미 DENSE 를 이겼다.
4. "옵티마이저가 horizon 을 쓸 이유를 못 찾았다" → 이득이 없었고 가중치가 거의 불변이었다는
   관찰까지만 성립한다. 왜인지는 규명 안 됨.
5. "이 계열은 중단을 권한다" → 중단 권고는 현재 고정 이웃 구현의 확대에 대한 것이고,
   목표 조건부 토큰 배분이라는 주제는 열려 있다.

### Jena — MPI-BGC 기상관측소 (WS Beutenberg / mpi_roof)

`https://www.bgc-jena.mpg.de/wetter/Weatherstation.pdf` (Olaf Kolle, 2025-02-04) 원문:

> "The sensors are scanned by the logger every 10 seconds - averages, totals and
> maxima of the variables over periods of 10 minutes are internally calculated and
> stored in the datalogger ring memory."

> "Date Time | dd.mm.yyyy hh.mm (MEZ) | Date and time of the data record
> (the timestamp represents the end of the averaging period)"

즉 공개된 10분 기록은 순간값이 아니라 **구간 통계**이고, **타임스탬프는 평균 구간의 끝**이다.

합계다. 따라서 core 채널은 `T (degC)` · `p (mbar)` · `rh (%)` 세 개, `rain`/`max. wv` 는 제외.

## 4. 계약 동결과 설계 결정

- `END_BIN` 은 수학적 순간값이 아니라 report interval 마지막 base bin(=10분 평균) 하나다.
  O 의 적분 basis 도 이 1-bin support 를 그대로 적분한다.
- O 와 M 의 유일한 차이는 관측 토큰의 time basis 다. Fourier basis 를 support 구간에서
  평균한 폐형식 `mean_[a,b] sin(wt) = sin(wc)·sinc(wd/2)` 을 쓴다 (학습 파라미터 없음).
  future query 는 M/O 동일(centre basis) — target 격자는 r 과 무관하게 10분 고정이라
  query 를 적분해도 해상도 정보를 나를 수 없고, 적분하면 M/O 차이가 둘로 늘어난다.
- window 적격성은 r·operation 과 **무관하게** 정의했다 (288 history + 72 target 전부 유효).
  그래야 모든 arm·op·r 이 정확히 같은 window 집합에서 채점된다.
- checkpoint 선택은 **학습에서 본 해상도(r=2,4,8)의 validation loss 만** 사용한다.
  r=3,6 을 모델 선택에 넣으면 "보지 않은 해상도"가 아니게 된다.
- R 의 λ 는 train/validation 만으로 고른다 — 후보 4개 각각에 대해 축소 예산(1/4) R fit 을
  seed0 에서 돌려 validation primary loss 로 dataset 당 하나를 동결. 사전등록 프로토콜.

## 5. 지시문 §36 진단의 문제와 대체

§36 의 "동일 batch 안에서 support width metadata 를 permutation" 은 이 batching 에서
**무연산**이다 — 한 batch 는 하나의 (r, op) 만 담으므로 모든 토큰의 width 가 같다.
증거를 `mechanism_diagnostics.json` 의 `within_batch_width_permutation` 에 남기고,
실제 효과가 있는 대체 변형 `WIDTH_MISMATCH`(다른 report interval 의 width 를 주입)를
돌렸다. `O-WRONG-SUPPORT`(centre basis 로 강제)는 지시문대로 O 에만 적용 —
M 은 이미 centre basis 라 항등이고 R 은 토큰 width 자체가 없다.

### 기전 진단 — O 는 support 를 실제로 쓰지만, 넓은 구간평균에서만 쓴다

처음에 연산을 평균해서 봤더니 흐려졌다. 연산별로 나누면 훨씬 선명하다.
추론 시 적분 basis 를 centre basis 로 바꿨을 때(O-WRONG-SUPPORT) 손실 증가:

| | r=2 | r=3 | r=4 | r=6 | r=8 | r=12 |
| --- | --- | --- | --- | --- | --- | --- |
| jena END_BIN | -0.55% | -0.10% | -0.36% | +0.32% | -0.15% | +0.53% |
| jena INTERVAL_MEAN | +0.42% | +1.56% | +0.57% | -0.09% | +7.93% | +7.81% |
| uci END_BIN | +0.05% | +0.10% | +0.06% | +0.07% | +0.03% | -0.03% |
| uci INTERVAL_MEAN | +0.04% | +0.18% | +0.03% | +0.14% | +0.65% | +1.00% |

END_BIN 은 r 과 무관하게 support 가 1 base bin 이라 적분 basis 와 centre basis 차이가
작다. 넓은 구간평균(jena INTERVAL_MEAN r=8,12)에서만 크게 무너진다. 이는 r=12 에서
O 가 M 을 이긴 유일한 cell (jena INTERVAL_MEAN +7.44%) 과 정확히 같은 자리다.
기전은 설계대로 작동한다 — 다만 사전등록 주 해상도(30/60분)에서는 값이 없다.

WIDTH_MISMATCH(다른 report interval 의 width 주입)는 M/O 어디서도 0.016% 이내다.
**주의**: END_BIN 에서는 이 변형이 구조적으로 무연산이다 — support 폭이 r 과 무관하게
항상 1 bin 이라 주입값이 참값과 같다. 정보를 담는 것은 INTERVAL_MEAN 행뿐이고 거기서도
평평하다. 즉 O 는 width 정보를 적분 basis 로 나르고, M 은 width 채널을 아예 안 쓴다.
이 사실을 `mechanism_diagnostics.json` 의 `end_bin_width_is_resolution_invariant` 에
기록했다.

## 오류 1 — FlowState native END_BIN 을 60분 평균으로 채점했다

END_BIN 예측은 각 report interval 의 **마지막 base bin 하나**다. 그 값들을 평균해도
그 시간의 평균이 되지 않는다. 나머지 r-1 개 bin 이 예측에 아예 들어가지 않기 때문이다.

base bin `[1,2,3,4,5,6]`, 참 시간평균 3.5 일 때 **완벽한** END_BIN 예측기조차:

| r | END_BIN 예측 | 평균 | 편향 |
| --- | --- | --- | --- |
| 2 | [2,4,6] | 4.0 | +0.5 |
| 3 | [3,6] | 4.5 | +1.0 |
| 6 | [6] | 6.0 | +2.5 |

INTERVAL_MEAN 은 r∈{2,3,6} 에서 정확히 3.5 가 된다. 즉 이건 r 문제가 아니라 **연산**
문제인데, v1 의 `native_variant()` 는 `r not in NATIVE_HOURLY_TILING` 만 보고 END_BIN 을
통과시켰다. 그 행들이 잰 것은 모델이 아니라 연산 불일치다.

`references.py` 에 `can_form_hourly_mean_from_native(operation, r)` 를 넣어 계약을 코드에
드러냈다 (END_BIN 은 모든 r 에서 False). 실패 조건은 점수 대신
`NOT_EVALUATED_SEMANTIC_TARGET_MISMATCH` 로 저장된다. 기존 `flowstate_reference.json` 은
지우지 않고 `HISTORICAL_NUMBER_NOT_COMPARABLE` 로 표시했다. **핵심 결과와 무관** — 이건
선택적 native reference 에만 있는 문제이고 R/M/O 비교에는 쓰이지 않았다.

## 과장했던 해석 정정

- **"기전이 작동한다"** → 표현 의존성이 있을 뿐 우월성이 아니다. 직접 반례가 artifact 에

  같은 cell 에서 표현 민감도와 예측 우월성이 갈린다.
- **"복원 가능성이 R 역전의 원인"** → `reconstruction_quality.json` 은 dataset 당 **채널
  1개·window 200개**만 본다. "일관된다"까지는 되지만 인과는 아니다. 개입 실험이 없었고,
  R 은 복원 품질 외에 tokenization 경로 전체가 다르다.
- **"M/O 는 width 를 안 쓴다"** → "명시적 스칼라 width 채널의 민감도가 작았다"까지만.
  해상도는 토큰 수·간격·time basis·연산 임베딩으로도 들어온다.
- **"FlowState zero-shot"** → 가중치는 zero-shot 이지만 resampled variant 의 재구성 λ 는
  target validation 으로 골랐다. `MODEL_WEIGHTS_ZERO_SHOT + TARGET_VALIDATION_TUNED_PREPROCESSOR`.
- **"M > R 이므로 metadata 면 충분"** → M 과 R 은 metadata 외에 tokenization 경로가 다르다.
  두 기여가 분리되지 않았다.

## 지시문 대조에서 추가로 찾은 누락 2건

"지시문 다 했나" 를 절별로 대조하다 두 가지가 빠진 것을 찾았다.

**§31 unit control 재확인을 안 했다.** `unit_contract.json` 을 불변 목록에 넣어 해시만
했고, SUM = r × MEAN 등가성이 허용오차 안인지 다시 보지는 않았다. 채워 넣었다 —
12개 모델 전부에서 표현 차이 0.0, 예측 차이 0.0, `UNIT_CONTRACT_HOLDS`.
SUM 은 단위 통제이지 성능 arm 이 아니라는 점을 STATUS §19 에 명시했다.

**§6 을 최소만 했다.** seed 별 미학습 보간 macro 두 줄만 냈는데, 지시문은 source 가
있으면 dataset × operation × r × seed 별 RI 를 요구한다. raw error 가 로컬에 있으므로
가능했다. 48개 cell 행 + 6개 macro 행으로 확장했다. seed 2개로 표준오차·CI 를 만들지
않는다는 제약은 유지했고 테스트로 강제한다.

확장하니 새로 보이는 것이 있다 — **R 대비 우열이 dataset 뿐 아니라 seed 간에도 뒤집힌다.**
미학습 보간 macro 기준:

| seed | O vs M | O vs R | M vs R |
| --- | --- | --- | --- |
| 2026090601 | -0.300% | -0.225% | +0.088% |
| 2026090602 | +0.202% | +1.338% | +1.135% |

세 대비 모두 seed 간에 부호나 크기가 크게 바뀐다. pooled R 비교 하나에 실을 수 있는
무게의 상한을 보여준다. STATUS §12 에 넣었다.

**§33 은 요건을 이미 만족했으나 실행 경로가 없었다.** 커밋된
`bootstrap_block_sufficient_stats.csv` 만으로 재생성되는지 실제로 돌려 확인했고
(-0.0544 [-0.2793, +0.1746], 저장값과 일치), `--from-stats-only` 플래그를 추가해
raw error 없이도 저장소만으로 재현 가능함을 실행으로 보이게 했다.
